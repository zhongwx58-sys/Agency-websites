# 组织排错材料

记录版本、脱敏参数、日志、复现步骤、处理与恢复结果。

## 让问题可以重复出现

一份好的排错材料先说具体操作与实际结果：在哪个系统和客户端中，启用了哪份配置，对哪个目标做了什么，出现了什么错误。再写预期行为和第一次发生时间。避免只说“无法使用”或“网络很慢”，也不要先给没有证据的根因，让观察事实与推测分开。

## 准备必要且脱敏的证据

保留客户端与内核版本、最小相关配置、时间对应的日志、连接记录和截图。密码、订阅令牌、二维码与不相关个人信息应遮挡；错误行和相关引用关系则要保留。用编号连接复现步骤与证据文件，使协助者可以沿时间线判断失败位置，而不需要猜测截图顺序。

```text
现象与预期：
系统 / 客户端 / 内核：
开始时间与最近变更：
最少复现步骤：
相关配置（已脱敏）：
错误文本与对应时间：
已验证事实：
尝试过的处理及结果：
恢复结果：
仍待核实：
```

## 把处理结果写成可核对结论

每次尝试写明改了什么、为什么改、怎样验证以及是否恢复。失败尝试也要保留，减少重复操作。问题暂时不再出现时写清观察时长和覆盖范围，不直接宣布永久修复。完成复盘后保存最后可用配置与恢复方法，把确认有效的结论补进对应课程，其余保持待核实。

## 常见误区

删掉关键错误只保留结论，或把短时未复发写成根因已经修复。

## 恢复与回退

恢复最后可用版本，补齐恢复后的验证记录；未解决部分继续保留，避免覆盖原始证据。
